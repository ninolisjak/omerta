# 4. Saving and the HUD

Goal: understand how browser persistence and the redesigned interface fit around the rules.

## Saving

`GameStore` writes a JSON snapshot under `omerta.game.v1` in `localStorage`. It saves after each command, about every five seconds, and on `pagehide`. Loading validates the snapshot before advancing it to the current time.

The version field gives us a place for future migrations. A new state shape must not silently interpret an old save as the new format. For now, unreadable saves start a fresh round with a visible warning.

Storage can fail, for example when disabled by browser settings. The store catches that error and shows a warning. Do not assume `localStorage` always succeeds.

Use one tab for a game. This prototype does not coordinate simultaneous writers. Clearing browser site data deletes progress. A private hosted URL does not turn local storage into a cloud database.

## What saving does not provide

Local storage is user-controlled. A player can edit cash or change their system clock. Validation prevents malformed data from accidentally breaking the UI; it does not establish trust. A competitive game needs server authority, which is the next chapter.

## The new HUD

The layout has four layers:

1. Left navigation and player identity.
2. A quiet top bar for location, round time, and settings.
3. A horizontal resource ledger with clear resource names.
4. Main work area: city view and operations, alongside empire intelligence.

The city artwork carries the atmosphere. The current interface uses grayscale surfaces, square frames, monochrome icons, and readable monospace type inspired by classic handheld RPG menus. The top-down pixel map replaces the original painted isometric artwork. Body text is 15–16 pixels, labels never drop below 12 pixels, and disabled actions keep readable contrast. See [Chapter 6](06-readable-pixel-ui.md) for the reasoning behind this redesign.

The map uses one background image and HTML district buttons. Positions are percentages. Each button selects a district and updates an information card below the map; its action navigates to the relevant screen. Zoom scales both the art and markers together. `image-rendering: pixelated` preserves hard pixel edges while scaling. District ownership is deliberately limited to your initial block; the other markers are opportunities and context, not a simulated multiplayer map.

## Responsive behavior

The main layout uses CSS Grid. As width shrinks, the right column moves under the map. Fronts and crew cards reduce columns. At 900 pixels and below, the sidebar becomes a navigation drawer. The resource ledger becomes two columns, while type remains readable.

Key classes live in `src/styles.css`; map-specific styles live in `city/city.component.css`. The smoke script checks every navigation screen at six widths, from 320 to 1920 pixels, and checks that rendered interface text stays at least 12 pixels.

## Accessible interactions

- Icon-only buttons have accessible names.
- Selected navigation uses `aria-current`.
- District selection and sound controls expose their state.
- A native `dialog` traps focus; Escape closes it and restores focus.
- Notifications use `role="status"`; save failures use alerts.
- Timers are not live regions, avoiding an announcement every second.
- Reduced-motion preferences are respected.
- Disabled actions show a reason as text, not just a hover tooltip.

The optional rain sound is generated by Web Audio after a user action. It does not autoplay or download an audio track.

## Try it

Change `--bg` in `styles.css` to a different gray and inspect the contrast between the background, panels, and labels. Then test at 390 pixels wide. A color or spacing change needs a quick small-screen check too.
